# 金融行业 IT 项目推进助手

把零散的客户信息，整理成**有事实依据的项目判断、信息缺口和下一步动作**。

适用于银行、保险、证券等金融机构的 IT 基础设施、存储、云、私有云、数据中心等项目推进场景。

## 它能做什么

你可以把会议记录、客户聊天、项目线索、招标信息、测试情况等资料直接交给它。

它会帮助你整理：

* 这个需求是谁提出的
* 实际使用部门是谁
* 预算来自哪个部门
* 预算是“计划中”“已申请”还是“已批准”
* 谁负责技术评估
* 谁影响技术选型
* 谁负责采购和招投标
* 谁是最终决策人
* 客户目前使用什么品牌和架构
* 现有供应商、集成商和原厂分别是谁
* 为什么会产生这次需求
* 是否存在明确的替换窗口
* 当前有哪些竞争对手
* 项目现在真正处于什么阶段
* 哪些信息已经确认，哪些只是推测
* 下一步最值得推进的两三个动作是什么

## 为什么需要这个 Skill

金融行业 IT 项目里，销售最容易犯的错误，往往不是不够努力，而是**过早下结论**。

例如：

* 客户说“预算有了”，就当成预算已经审批完成
* 把现用品牌、现有集成商和原厂混成一件事
* 听到客户提过测试，就默认已经进入正式 POC
* 看到存量是竞品，就直接判断这是替换项目
* 看到需求和华为产品相关，就预设最终方案一定是华为
* 把技术认可理解成采购认可
* 把一个联系人当成最终决策人
* 强行把项目套进“线索 → 测试 → 招标 → 中标”的固定流程

现实中的金融 IT 项目经常不是线性的。

测试可能发生在预算审批之前，技术交流和商务沟通可能长期并行，预算可能被推迟，项目可能重新立项，甚至已经进入招标阶段的信息也可能并不完整。

这个 Skill 的目标，就是尽量把**事实、判断和未知信息分开**。

## 核心设计

### 1. 先拆角色，再判断关系

不会默认“客户”是一个统一角色。

会分别识别：

* 需求提出方
* 实际使用部门
* 技术评估方
* 架构或基础设施团队
* 信息科技部门
* 预算归属部门
* 采购部门
* 项目负责人
* 关键影响者
* 最终审批人

同一个人可以承担多个角色。

如果资料里没有出现某个角色，不会自行补齐组织结构。

### 2. 所有重要信息都区分事实等级

关键信息会尽可能标记为：

**已确认事实**
有客户明确陈述、会议记录、邮件、招标文件或其他资料支持。

**合理判断**
根据已有事实可以推断，但没有直接证据。

**待确认**
目前信息不足，需要继续向客户、原厂、伙伴或项目相关方确认。

重要信息尽量保留来源和日期。

没有证据，就不把推测写成事实。

### 3. 不把品牌和解决方案预设成结论

不会因为：

* 客户现在使用竞品
* 客户曾经测试过某品牌
* 销售代理某个厂商
* 某个产品技术上符合需求

就直接判断最终应该采用某个品牌或方案。

先理解客户现状、需求、约束、预算、迁移成本和决策机制，再判断机会。

### 4. 项目阶段是判断，不是固定模板

系统会根据现有证据暂定项目阶段，例如：

需求发现、需求澄清、方案交流、预算准备、立项、测试验证、商务准备、采购招标、实施交付等。

这些阶段可以：

* 并行
* 回退
* 重复
* 跨阶段发生

因此阶段只代表**当前最合理的工作判断**，不是强制流程。

### 5. 不用一张巨大问卷审问客户

信息不足时，不会一次抛出几十个问题。

它会：

1. 先根据已有资料做当前判断
2. 找出影响项目判断最大的几个信息缺口
3. 一次只建议确认 2–3 个问题
4. 根据新的答案继续更新项目判断

## 典型输出

输入一段零散的客户信息后，可以得到类似这样的结构：

**项目判断**

目前更像处于需求确认 / 预算准备阶段。

**判断依据**

客户已经明确提出容量扩容需求，并开始与厂商进行方案交流，但目前没有证据证明预算已经正式审批。

**已确认**

* 当前存储品牌：A
* 使用部门：核心系统团队
* 有扩容需求
* 已经进行过一次技术交流

**待确认**

* 预算归属部门
* 预算是否已经进入年度计划
* 是否存在正式替换现有存储的计划
* 最终技术决策人

**主要风险**

目前不能因为客户愿意测试，就判断项目已经进入采购阶段。

**下一步**

1. 确认预算状态及预算归属
2. 确认此次需求是扩容、替换还是新建
3. 确认技术选型和最终审批分别由谁负责

## 方法来源

这套方法来自作者多年金融行业客户与 IT 项目销售实践，并由 AI 辅助整理为可重复执行的结构化流程。

它提供的是**项目分析和推进辅助**，不是自动成交工具，也不能替代客户沟通、技术判断、商务谈判或组织关系建设。
